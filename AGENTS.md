# Инструкции для Matcha Wiki

Этот публичный репозиторий одновременно хранит исправленную русскую Matcha
Flavoured 1.03 для Minecraft 26.2 и статическую энциклопедию по ней.

## Источники истины

- `pack/` — каноническое распакованное дерево hybrid data/resource pack. ZIP
  всегда собирается из него; не правь архив отдельно.
- `scripts/generate-wiki-data.ts` извлекает предметы, рецепты, достижения,
  источники и ассеты прямо из `pack/`.
- `content/wiki/` хранит редакционные статьи и гайды. Точные числа, рецепты и
  свойства сначала доказывай по игровым данным, а затем объясняй текстом.
- `wiki-data/vanilla-ru-26.2.json` — зафиксированный источник ванильных русских
  названий именно для 26.2.
- `wiki-data/fixes/*.json` — публичный реестр подтверждённых исправлений.
- `generated/`, `public/generated/`, `.output/` и `dist/` производны. Не
  редактируй и не коммить их вручную.

Namespace, item model ID, recipe ID, advancement ID и пути ресурсов являются
контрактом совместимости с существующими мирами. Не переименовывай их ради
красоты.

## Исправления пака

Не называй изменением баланса или предположением исправление. Для bugfix нужны:
точный источник, воспроизводимое неверное поведение, причинная правка и
регрессионная проверка.

После изменения `pack/`:

- добавь или обнови запись в подходящем `wiki-data/fixes/*.json`;
- проверь все ссылки, JSON/MCMETA и затронутую игровую цепочку;
- для selector, tick, schedule, scoreboard и enchantment logic отдельно
  проверяй multiplayer-владельца command source;
- если результат зависит от семантики Minecraft, проверь его на официальном
  сервере 26.2, а не только парсером;
- не добавляй авторские wishlist-функции в 1.03 без законченной реализации,
  проверки и явной записи в changelog.

Ограничение, которое нельзя безопасно исправить data-driven средствами, должно
оставаться видимым как deferred/known issue, а не скрываться рискованным
fallback.

## Nuxt, Vue и стили

- Используется Bun, Nuxt, Vue, Nuxt Content и SCSS. Сначала переиспользуй
  существующие компоненты, composables и генератор данных.
- Keep Vue SFCs ordered as `<template>`, `<script>`, then `<style>`.
- Keep component styles next to their markup in `<style scoped lang="scss">`.
  Put only shared tokens, resets, and genuinely global rules in
  `app/assets/styles/`; do not grow a detached page-level stylesheet.
- Use nested SCSS where it makes the component hierarchy clearer, without
  BEM-style class names or deeply coupled selectors.
- В Markdown Nuxt Content закрывай пользовательские Vue-компоненты явным
  парным тегом. Запись `<RecipeById ... />` обрывает отрендеренную статью после
  вставки; используй `<RecipeById ...></RecipeById>`.
- Не используй декоративные numbered markers, стат-бейджи и одинаковые карточки
  как автоматический scaffolding. Номера допустимы только там, где они несут
  реальный смысл, и должны быть оформлены спокойно, без “AI dashboard”
  квадратных плашек.
- Не используй разделительные линии как основной способ группировки: смысловые
  блоки разделяй отступами. В плотных повторяющихся списках допустимы линии
  только между соседними элементами, без рамок в начале и конце списка.
- Сохраняй minecraft-выразительность через реальные текстуры, item slots,
  tooltip и ясную типографику, а не через декоративный шум, градиенты и
  card-in-card.
- Любая новая раскладка должна быть пригодна для клавиатуры и проверена в
  Microsoft Edge как минимум на desktop и mobile viewport.

## Команды

```text
bun ci
bun run dev
bun run data
bun run pack:normalize --check
bun run lint
bun run typecheck
bun run test
bun run generate
bun run pack
bun run validate
```

`bun run validate` — обязательная полная локальная проверка перед delivery. Она
генерирует данные, запускает lint/typecheck/tests, пререндерит все страницы и
собирает воспроизводимый ZIP с SHA-256.

## Git, CI и секреты

Репозиторий публичный. Не коммить ключи, токены, cookies, `.env`, локальные пути
с секретами, сохранённые сессии и дампы. Не печатай такие значения в логах,
issues, release notes и ответах.

Push в `main` запускает проверки и GitHub Pages. Тег `v*` собирает GitHub
Release с ZIP и `SHA256SUMS.txt`. Перед тегом локальный `bun run validate`
должен проходить на том же дереве.

Сохраняй сторонние кредиты и условия CC BY-NC-SA 4.0. Не удаляй
`pack/CREDITS.txt`, `LICENSE.md` и `TRANSLATION.md` из релизного происхождения.

## Качество изменений

Главный приоритет — чистый, простой, сильный итоговый код в контексте всей
кодовой базы. Минимальность означает отсутствие лишнего кода, состояния,
абстракций и неверного слоя, а не минимальное число строк в patch.

После каждого смыслового изменения пересматривай diff как строгий ревьюер:
удаляй unused imports, методы, файлы, fallback-ветки, одноразовые wrapper-ы и
следы промежуточной гипотезы; перепроверяй архитектурные границы, источник
истины и затронутый пользовательский сценарий.

«"Работает" недостаточно. После того как довел до рабочего состояния, убедись,
что решение встроено в код красиво и без временных подпорок. Если по пути
пришлось оставить костыль или фоллбэк, потом обязательно добейся его удаления,
даже если для этого надо явно попросить пользователя сделать связанное
изменение.»

Если пользователь в ходе работы даёт новые устойчивые правила по стилю кода,
структуре или процессу, то их надо кратко и по делу сразу добавлять в этот файл
`AGENTS.md`, если это реально полезно будущим агентам.

Правила в `AGENTS.md` добавлять только если пользователь явно просит сохранить
что-то универсальное и долговременное; не заносить туда ситуативные
договорённости текущей задачи.
